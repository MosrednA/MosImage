# Klein in MLX, 8-bit and 4-bit, against the BF16 port on Apple silicon — 11 October 2026

Status: **integrated behind `MOSIMAGE_APPLE_WEIGHTS`** (`bf16`, `q8`, `q4`). By default a Mac picks by unified memory: BF16 from 64 GB, 8-bit from 48 GB, 4-bit below that. The M5 Max this was measured on keeps BF16.

The question was whether MLX 4-bit and 8-bit weights save memory on a Mac while masked edits, references and LoRAs keep working, compared against the BF16 PyTorch port. They do. Measured through the app's own services on all 11 cases, 8-bit lowers Quality's peak from 36–42 GiB to 24–30 GiB and 4-bit to 18–24 GiB. Every job ran: masked edits, references, Consistency, the detail enhancer and Specialized outpaint. 8-bit images are as close to BF16 as an unquantized MLX run is. 4-bit keeps the scene but changes details. Both cost 4–7% in time.

## Approach

MosImage's Klein pipelines are diffusers' `Flux2KleinPipeline` and `Flux2KleinInpaintPipeline`. References, masks, partial strength, the scheduler and the VAE all live in those pipelines. Only two components are large: the transformer (9B: 16.9 GiB in BF16) and the Qwen3 text encoder (9B: 11.2 GiB, trimmed). [`klein_mlx.py`](../backend/app/models/klein_mlx.py) reimplements those two in MLX and puts torch-shaped wrappers in their place, so the pipelines run unchanged.

- **Transformer.** A port of diffusers 0.41's `Flux2Transformer2DModel`: double- and single-stream blocks, 4-axis RoPE, AdaLN modulation. It keeps diffusers' layer names, so checkpoints load without renaming and LoRA targets match. The pipelines call it as before and read only `config.in_channels`, `dtype` and `cache_context()`. The reference KV-cache mode is not implemented, because MosImage's pipelines never use it.
- **Text encoder.** The first 27 Qwen3 decoder layers, which is all Klein reads (hidden states 9, 18 and 27). It answers the pipeline's `text_encoder(input_ids, attention_mask, output_hidden_states=True)` call.
- **Quantization.** MLX affine quantization with groups of 64, applied at load one block at a time from the original BF16 safetensors. Only the blocks' linear layers are quantized (about 96% of the weights). Embedders, modulation, norms and the output projection stay BF16.
- **Interop.** MLX 0.32 shares Metal buffers with PyTorch through DLPack, so latents, prompt embeddings and results cross without a copy after an MPS synchronize. The prompt embedding is converted once per job, not once per step.
- **LoRA.** [`KleinLora`](../backend/app/models/klein_lora.py) converts an adapter to diffusers names as before. For the MLX transformer it then attaches each pair as a BF16 low-rank residual beside the BF16 or quantized linear (`LoraLinear` in `klein_mlx.py`). The base weights are never dequantized or merged, the scale can change per job, and `detach()` restores the original layers.

mflux 0.22 (MIT) has an MLX Klein too, but not for masked editing, and its LoRAs are fixed at load. It was used for the first measurements and as a reference. The app depends only on `mlx==0.32.3`.

## Numerical checks

Run with random inputs at 1024² on the real checkpoints, plus unit tests on tiny random models ([`test_klein_mlx.py`](../backend/tests/test_klein_mlx.py)).

| Comparison | Relative error | Cosine |
|---|---:|---:|
| diffusers BF16 against diffusers FP32 (the BF16 noise floor, 4B) | 7.7% | 0.9971 |
| MLX BF16 against diffusers BF16 (4B) | 2.7% | 0.99965 |
| MLX BF16 against diffusers FP32 (4B) | 7.6% | 0.9971 |
| MLX q8 against diffusers BF16 (9B transformer) | 4.0% | 0.9992 |
| MLX q4 against diffusers BF16 (9B transformer) | 26% | 0.965 |
| MLX encoder BF16 / q8 / q4 against transformers (9B, layers 9/18/27) | 0.01–0.09% / 0.6% / 2.7–3.0% | 1.0 / 0.99998 / 0.9997 |

The port is as accurate as diffusers itself. The q8 encoder is closer to BF16 than the FP8 encoder the Windows profile streams (0.6–3.7%), and q4 is about equal to it. The unit tests also check LoRAs: on BF16 and 4-bit weights the MLX adapter's effect matches the torch adapter's within 2% (BF16) and 10% (4-bit). Scale zero is exact, and `detach()` restores the original layers.

## Benchmark

[`benchmark_mlx_klein.py`](../backend/tools/benchmark_mlx_klein.py) runs every case through the app's services (`run_text_to_image`, `run_image_edit`, `run_inpaint`, `run_outpaint`, `run_enhance`). Masked edits therefore get the editor's crop, inpaint mask and compositing, references come from the reference store, and LoRAs attach through the providers. Each arm runs in its own process with its own database and image folder. Like the job runner, the tool releases the GPU caches after every job.

Setup: Apple M5 Max (40-core GPU, 128 GB), macOS 27.0.1, Python 3.13.15, PyTorch 2.14.1, diffusers 0.41.0, transformers 5.19.0, MLX 0.32.3. Weights are the pinned BF16 checkpoints the app uses: 9B revision `92196c8e`, 4B revision `e7b7dc27`. Four steps, guidance 1, seeds 7 and 42. All 88 renders across the four arms succeeded.

**Cases.** Quality (9B):
- text to image at 1024²;
- two people from two references at 1216 × 832;
- a whole-picture edit (portrait to DJ), with and without the Consistency LoRA;
- a masked replace, with and without Consistency;
- a masked remove;
- a masked insert from a reference (a mug);
- Enhance on a face selection (detail-enhancer LoRA at strength 0.4, partial redraw, tiled).

Fast (4B):
- a masked replace (phone to sword);
- Specialized outpaint with fal's LoRA.

**Arms.** `bf16` is the current port. `q8` and `q4` are MLX. `mlx-bf16` is a control: MLX without quantization, which separates what the implementation changes from what the bits change.

**Memory** is the process's physical footprint (Activity Monitor's Memory column), sampled every 20 ms. On Apple silicon it includes every Metal allocation of PyTorch and MLX.

Relative to BF16, the median job takes 2.7% longer in MLX BF16, 6.7% longer in q8 (range 4–13%) and 3.8% longer in q4. With thousands of tokens per step, MLX's quantized matmul is no faster than the M5 Max's BF16 matmul: smaller weights save memory, not time.

**Visual review** of every pair (`gallery.html` and `sheets/`):
- **q8** keeps composition, identity, objects and light. The differences are fine details: a fur strand, a knob on the mixer, a fold.
- **MLX BF16 differs from PyTorch BF16 by about as much** as q8 does. Two BF16 implementations round differently, and four denoising steps amplify that into different fine detail. Most of q8's distance from the port is therefore not quantization.
- **q4** keeps the scene, the identities from references and the edited object. It changes framing and details more, for example the mug's handle in the reference insert, the framing of the DJ and the fox's size. No artefacts or banding were seen, and 1:1 crops of the fox and of the Enhance face are as sharp as BF16.
- **LoRA cases run in every arm** and stay as close to BF16 as the cases without a LoRA. Enhance with the detail enhancer is near-identical in q8 (48.6 dB in the selection), and fal's outpaint LoRA extends the garden without a seam in all three.

## Releasing the GPU caches between jobs

PyTorch (the VAE) and MLX (transformer and encoder) each keep freed Metal buffers for reuse. Both count against the same unified memory, and MLX's cache grew to 5.9 GiB when jobs of different sizes alternated. The job runner now empties both caches after every GPU job, on Apple silicon only (`runtime.release_cached_memory`). CUDA's caching allocator is untouched.

Measured on Quality, with a 1024² generation and a masked replace alternating three times:

| Weights | As before: peak / idle | Released after each job: peak / idle | Time |
|---|---:|---:|---|
| BF16 | 40.5 / 40.4 GiB | 37.6 / 35.4 GiB | unchanged |
| q8 | 30.9 / 30.9 GiB | 25.5 / 24.2 GiB | unchanged (7.31 against 7.34 s, 12.58 against 12.56 s) |
| q4 | 24.4 / 24.4 GiB | 19.0 / 17.7 GiB | unchanged |

A 1 GiB cap on MLX's cache instead (`mx.set_cache_limit`) brought q8 to 24.1 GiB but slowed masked edits by 9%, so it is not used.

## Where the rest of the peak goes: the VAE

Even 4-bit Fast, with 4.4 GiB of weights, peaks at 16 GiB, and the excess is the same in every arm. It is diffusers' Flux2 VAE on MPS. One decode of 1024² allocates 6.5 GiB of Metal memory. At 1216 px it allocates 9.0 GiB with the default tiling (1024 px tiles) and 14.2 GiB without. With 512 px tiles it allocates 1.3 GiB (1024²) and 3.4 GiB (1216), and decoding takes 0.44 s instead of 0.36 s at 1024².

Round trips through the VAE on three fixture photos give 39.6–43.1 dB between tiled and untiled. That is less than the VAE's own round-trip error against the source (31.4–41.0 dB), and no seam is visible even when the difference is amplified eight times.

This would lower every Mac arm's peak by roughly another 5–10 GiB, BF16 included. It is a separate change (the VAE's tile size on Apple silicon) and is not part of this one.

Follow-up: decoding alone, as generated images are, 512 px tiles measure 26–31 dB against untiled. Only Macs without room for Quality use them now. See the [note](../docs/notes/2026-10-11-apple-vae-tiles.md).

## Defaults and limits

`default_apple_weights` maps unified memory to weights:

| Unified memory | Weights | Warm-up model |
|---|---|---|
| 64 GB and up | BF16 | Quality |
| 48–63 GB | q8 | Quality |
| 36–47 GB | q4 | Quality |
| Under 36 GB | q4 | Fast |

Quality warms up when its measured peak (43 / 31 / 24 GiB) plus 12 GB for macOS and the UI fits. `MOSIMAGE_APPLE_WEIGHTS` and `MOSIMAGE_WARM_UP_MODEL` override both. The model menu shows the weights in use, for example "FLUX.2 Klein 9B (8-bit)".

Limits:
- Only the M5 Max was measured. The thresholds for smaller Macs come from these footprints and were not tested on such machines. Other chips will also differ in speed.
- Quantization runs at every load (about 6 s for 9B from a warm page cache). A first load reads the BF16 checkpoints from disk like the PyTorch port does.
- The transformer's reference KV-cache mode is not ported.

## Reproduce

```bash
cd backend
.venv/bin/python tools/benchmark_mlx_klein.py --output ../data/mlx-klein-2026-10-11 --arms bf16,mlx-bf16,q8,q4
.venv/bin/python tools/benchmark_mlx_klein.py --output ../data/mlx-klein-2026-10-11 --compare --arms bf16,mlx-bf16,q8,q4
.venv/bin/python -m unittest tests.test_klein_mlx
```

`data/mlx-klein-2026-10-11/` (not committed) keeps the assets with their hashes, each arm's `results.json`, every render, `summary.json`, `gallery.html` and the side-by-side sheets. The first run without the per-job release is kept as `results-without-release.json`.
