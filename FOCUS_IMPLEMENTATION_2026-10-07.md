## Overall interface

The English editor uses the same canvas-first shell for generating, selecting, painting masks, replacing/removing content, expanding and comparing proposals.

- A 52 px header and 64 px tool rail replace the larger permanent UI blocks.
- The image uses the remaining workspace above a compact command dock. Nothing overlaps the fitted image.
- Generation settings, including quality, count, aspect ratio and advanced inference controls, open a modal panel.
- Regional edits expose Edge blend, Surrounding context and optional Scene notes in that panel. Defaults use 320 px context and a 16 px transition, retained during Klein sampling and final blending. A toggleable dashed rectangle shows the context the model sees; it remains protected.
- Control modals keep their heading and Done action visible while longer settings scroll, including narrow windows.
- Canvas size opens a modal with format presets and exact margins; expansion handles remain directly on the canvas.
- Selection controls follow the active tool. Refine selection opens a contextual popover instead of occupying a permanent row.
- The proposal review strip replaces the instruction dock. Compare original, select an alternative, Apply or Discard.
- Cancel replaces the primary instruction action for queued, loading, selection and generation jobs. Cancelling stays visible while memory is released, locks new submissions, and recovers from a supervised worker replacement without a misleading missing-job error. The current image, prompt and selection remain available afterward.
- Library opens a searchable drawer; document names autosave. Open, export, document undo/redo, Fit and zoom remain directly accessible.
- Narrow screens retain a viewport-sized workspace, using a horizontal tool rail and compact controls. This is browser responsiveness, not a packaged mobile application.

At a 1920 × 936 viewport, the original 1152 × 864 fixture displays at 859 × 644. With 128 px on each side, the expanded canvas displays at approximately 786 × 625, compared with approximately 261 × 208 in the rejected layout. These are browser layout measurements, not image-resolution or model-performance claims.

## Local selection and expansion

SAM 2.1 Tiny uses the public `facebook/sam2.1-hiera-tiny` checkpoint through Transformers. Point coordinates are native image coordinates; click includes and Alt+click excludes. Requests allow at most 24 points and require a positive point. One image embedding is cached by content hash. The selection model stays on CPU, leaving GPU memory to the serialized generation worker. Manual brush, erase, rectangle, lasso and mask transforms remain available.

`POST /api/select` accepts an image plus validated JSON point parameters and returns a queued selection job. Completed jobs expose a local mask URL, separate from generation IDs.

`POST /api/outpaint` accepts an image plus validated JSON generation parameters and margins. It creates an extended RGBA canvas and a mask selecting only added margins, then uses the existing model provider and compositor. Original RGBA pixels are preserved exactly; added pixels become opaque. Native dimensions are capped at 4096 per edge and 16 million pixels; model input remains capped at 1024 on its longest edge. Outpainting quality depends on the selected model and scene.

Proposals bind to their source revision. Applying, undoing, redoing or reopening restores both the corresponding image and canvas dimensions. Quality editing now uses the native `Flux2KleinInpaintPipeline` in the installed Diffusers 0.41.0, with the actual mask and edit strength. Generation and inpaint pipelines share weights but are loaded separately, with one resident at a time. Protected compositing still enforces exact original pixels outside the selection. Expand automatically selects Z-Image Turbo at 8 steps and guidance 0, labeled Standard. The API also accepts the optional FLUX Fill adapter, but its BF16 component-offload implementation does not make the entire 12B transformer fit the 16 GB GPU; a quantized or finer-grained route remains unimplemented and unvalidated. The API rejects Klein for outpainting; the new native Klein path has not been evaluated for expansion.

## Runtime refactor validation, 8 October 2026

The maintenance refactor adds named, idempotent SQLite migrations with WAL, limits HTTP file access to the image directory, caps per-file upload reads, expires finished job records after ten minutes, serializes subject isolation on the CPU selection worker and returns typed revision conflicts as HTTP 409. Library deletion removes documents or generation history, retaining generation inputs/masks used by another generation and preserving documents' copied results.

Review found three defects: Z-Image's component reuse defaulted to FP32, document deletion skipped layer assets, and the upload size check ran after an unbounded read. Task switches now pass the runtime dtype explicitly; deletion collects layer images/masks from every deleted revision and preserves any still referenced by other revisions; upload reads stop after the configured limit plus one byte. Regression cases reproduce the earlier failures and cover shared historical layer assets and an upload exactly at the limit.

The dtype regression uses the installed Diffusers pipelines with tiny CPU modules and verifies BF16 plus component reuse in both task directions. It does not load model weights or establish new CUDA memory, speed or image-quality measurements. Earlier GPU and browser evidence above belongs to the dated validations described there; the maintenance changes require a backend restart to affect an already running local app.

Validation on 8 October: 96 backend unit tests and 46 frontend unit tests pass; Python compilation and the frontend TypeScript/Vite build pass. The updated README, implementation reference and roadmap have 24 verified local file/heading links. Backend checks use an isolated database and temporary directory under `data/`, preserving the user's live documents and running engine.

## AI results as layers, 9 October 2026

The command dock now offers Generate alongside Replace and Remove in an open document. Generate needs no selection; Apply adds the full image at the canvas centre, scaled to fit while preserving its aspect ratio. Its preview uses the same placement over the existing visible picture. New starts a separate document, where the first image remains the background.

Replace and Remove always produce a new layer, including empty stacks and stacks whose layers are all hidden. The model still sees the visible composite. The new layer is cropped to the actual selection footprint and preserves the already blended proposal pixels. The editor converts opaque greyscale selection PNGs to alpha coverage before finding that footprint; previously their fully opaque alpha could turn the patch and its stored mask into a whole-canvas overlay. The stored footprint mask is binary because the proposal already includes the feathered blend. Applying the original soft selection again would blend that edge twice.

Apply waits for the layer revision to save before closing review. A failed save restores the saved stack and keeps the proposal available for retry. Successful Apply opens Layers and selects Transform. Blend in still adds its copy above the original and hides the original. Expand keeps its existing background and canvas-dimension route. There are no provider, model, schema or API changes.

An isolated API with real layer assets, SQLite revisions and deterministic generation outputs verified regional edits over an empty stack, another edit with all existing layers hidden, full generation on the same document, removal with visible layers, Hide, Undo/Redo, reopening and retry after an injected HTTP 409. The assembled layer image matched the feathered inpaint proposal with **zero differing channels** across 512 × 512 RGBA pixels. A 1344 × 768 full generation fitted to a 512 × 512 canvas also matched its preview with **zero differing channels**. Widths 320, 390 and 1440 had no horizontal overflow. Test data and the fixture API are under `data/layer-results-validation/`. These checks validate editor behavior and persistence; inference was stubbed and establishes no new model-quality or GPU-performance results.

Validation on 9 October: 48 frontend unit tests and 97 backend unit tests pass, along with Python compilation, the TypeScript/Vite build and the Tauri release build (`--no-bundle`). The desktop executable at `frontend/src-tauri/target/release/mosimage.exe` was rebuilt after the app closed. All 37 local documentation file/heading links passed inspection. The isolated validation servers were stopped after the browser checks.

## Klein 9B Quality default, 9 October 2026

A side-by-side comparison of 216 retained renders (twelve cases, three seeds, six arms) found Klein 9B NVFP4 better than 4B on reference inserts, held-object swaps and two-person scenes, at a 3.8 s median against 2.4 s. Qwen-Image 2.1 turbo was strong on whole-image edits but weak on masked work at 17.8 s. The [model comparison](benchmarks/MODEL_COMPARISON_2026-10-09.md) has the method and full results.

`flux2-klein-9b-nvfp4` is now the default for generation, editing, preload and start-up warm-up, and the Quality preset in the UI. `Flux2Klein9bNvfp4Provider` reuses the NVFP4 loader with the 9B revisions. It replaces the 16 GB BF16 encoder with `klein_text_encoder.py`: the 28 Qwen3-8B layers Klein reads, per-row FP8 projections and a CPU token embedding, pinned in RAM and copied to the GPU per new prompt. Transformer and VAE stay on CUDA in every memory mode. The NVFP4 loader's module count is now an upper bound, since 9B keeps its first block's QKV in BF16. 4B NVFP4 and BF16 stay registered, and Advanced controls state the 9B non-commercial licence. References and Klein-specific routing accept all three Klein models.

Through the real provider on the RTX 5070 Ti, load plus warm-up took 25.4 s and a 1024 × 1024 generation 3.2 s. A full-frame 832 × 1216 edit took 7.3–7.8 s, at a peak of 10.9–11.0 GiB PyTorch allocation and 10.5 GiB process RAM. Other desktop applications already used 5.7 GB of the card, and the card peaked at 15.4 GB. Unloading returned the card to 3.7 GB.

Validation on 9 October: 98 backend unit tests (including a new 9B provider test) and 48 frontend unit tests pass, along with Python compilation, the TypeScript/Vite build and the Tauri release build. The FP8 encoder was checked against the full BF16 encoder on one prompt and the app renders spot-checked visually; there is no paired quality evaluation of FP8 against BF16 embeddings.
